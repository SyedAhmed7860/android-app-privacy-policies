Audited Technical Security Controls

Security Architecture & Data Protection

Application: ReceiptVault Package Name: com.receiptvaultapp Platform: Native Android 8.0+ to Android 16 (API 36)
Grounded Security Transparency

We do not make exaggerated claims such as "military-grade encryption" or "uncrackable systems." Below is an exact technical breakdown of the defensive architectural mechanisms and cryptographic controls physically implemented in ReceiptVault's source code.

1. Android Application Sandboxing

ReceiptVault relies on the core Linux kernel process isolation and application sandboxing inherent to the Android operating system:

  • Unique Linux UID: Each installation of ReceiptVault is assigned a distinct user identifier (UID) by the Android OS. Other applications on your phone run under separate UIDs and are strictly prohibited from reading or executing files belonging to ReceiptVault.
  • Internal Storage Isolation: Receipt images are stored in context.filesDir/receipts (physically located at /data/user/0/com.receiptvaultapp/files/receipts). This directory has file system permissions set to private (read/write only by ReceiptVault's UID).
  • No External Storage Leakage: Receipt images are never written to shared public directories (such as /sdcard/Download or public photo galleries) unless you explicitly initiate an export action.

2. App Lock Security: Salted SHA-256 & Biometrics

ReceiptVault features an optional App Lock mechanism (PIN or Biometric authentication):

  • Salted Cryptographic Hashing: Security PINs are hashed using the SHA-256 cryptographic digest combined with a unique application salt prior to storage. Plaintext PINs are never saved to disk, never cached in memory, and never logged.
  • Android Hardware Biometrics: Biometric authentication is implemented via the official androidx.biometric.BiometricPrompt library. ReceiptVault never accesses, receives, or stores your raw fingerprint or facial recognition data. Authentication is verified inside the Android device's hardware Secure Enclave / Trusted Execution Environment (TEE), which returns a binary authorization result to the app.
  • Configurable Auto-Lock: Users can configure immediate re-locking or background timeouts (15 seconds, 1 minute, 5 minutes) via the security manager.

3. SHA-256 Backup Payload Integrity Validation

To guard against data tampering, bit-rot, and corrupted file imports during cloud synchronization:

  • Pre-Upload Hashing: Before a backup snapshot is serialized and written to Google Drive, ReceiptVault computes a SHA-256 cryptographic checksum of the JSON payload.
  • Verification on Restore: Upon restoring a backup, the payload is reconstructed, re-hashed, and compared against the recorded checksum. If a hash mismatch is detected, the restoration process halts immediately with an error, preventing corrupt or tampered records from entering your database.

4. OAuth 2.0 & Restricted Google Drive Scope

ReceiptVault's Google Drive integration enforces strict least-privilege principles:

  • Restricted Scope (drive.file): We request only https://www.googleapis.com/auth/drive.file access. ReceiptVault cannot view, modify, or list files outside the ReceiptVault folder it creates.
  • Zero Photo Upload: The backup serializer strictly excludes local image file paths and image binary data. Only structured expense metadata is synchronized.
  • Secure Token Management: OAuth tokens are obtained via official Google Play Services Identity and exchanged exclusively with Google's servers over secure HTTPS/TLS.

5. Transport Layer Security (TLS/HTTPS)

Every network transaction executed by ReceiptVault (communicating with Google Drive, Google Play Billing, or Google Mobile Ads) enforces TLS 1.2+ encryption in transit. Cleartext HTTP traffic is disabled.
